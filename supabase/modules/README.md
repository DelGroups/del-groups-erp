# Module install scripts

Each module's part of the database schema lives in `supabase/modules/<id>/install.sql`,
next to the core baseline in `supabase/baseline/`. A fresh database is the core baseline
plus the install scripts of its modules, in the order of `ORDER` (dependencies first).

| File | What it is |
| --- | --- |
| `<id>/objects.json` | Hand-written: the tables, functions, sequences, views, buckets and storage policies the module owns. |
| `<id>/install.sql` | Generated by `python3 scripts/db/generate-baseline.py`. Never edit by hand. |
| `ORDER` | Module ids with an install script, in install order. |

Everything that hangs off a module's tables (column defaults, constraints, indexes,
triggers, RLS policies, grants, realtime publication) goes into its install script
automatically, and so does a core object that depends on it (a foreign key to a module
table, a trigger calling a module function, a view reading a module table). The core
baseline therefore builds on its own.

A foreign key between tables of two modules (for example `deals.production_order_id`: crm and
production do not depend on each other) is in both modules' install scripts, guarded so that it is
added only once both tables exist. Each module installs on its own, in any order, and the link
appears when the second one is installed (`tests/moduleSql.test.mjs` checks this).

## Changes

Schema changes are still one file in `supabase/migrations/` (see `supabase/baseline/README.md`).
When the baseline is refreshed from production, the generator splits the new snapshot into
core and modules again.


A tenant may be installed with only some modules (control panel provisioning). A migration that
touches a table owned by a module must therefore guard that part with
`IF to_regclass('public.<table>') IS NOT NULL THEN ... END IF;` (in a `DO` block), or the
migration fails on tenants without the module. `tests/moduleSql.test.mjs` checks this for every
migration newer than `supabase/baseline/VERSION`.
## Checks

- CI (`.github/workflows/db-baseline.yml`) regenerates the files and fails on any difference,
  builds core + modules on Postgres 17 and compares the result with the production snapshot.
- `tests/moduleSql.test.mjs` checks `ORDER` against the module dependencies in `src/modules`.

## Modules moved so far

- `crm`: `deals`, `quotations`, `next_quotation_number()`, `quotation_number_seq`.
  The `crm-assets` storage bucket stays in core (the company profile stores the logo and seal there).
- `contracts`: `contracts`, `validate_contract_legal_party()` (+ its trigger), the `contract-attachments`
  bucket and its storage policies, and the foreign keys `sales.contract_id` / `purchases.contract_id`.
- `consignment`: `consignment_partners`, `consignment_dispatches`, `consignment_inventory`,
  `consignment_monthly_reports`, `consignment_returns`, the older `consignments` / `consignment_items` /
  `consignment_orders`, and the RPCs `consignment_adjust_warehouse_stock()`,
  `create_consignment_dispatch_atomic()`, `set_consignment_initial_balance_atomic()`,
  `settle_consignment_partner_atomic()`.
- `commissions`: `commission_rules`, `employee_commission_rules`, `sales_commissions`, and the older
  `monthly_commissions` / `monthly_commission_details`. The payroll functions
  `calculate_monthly_payroll_drafts()` and `pay_payroll_run_atomic()` stay in core but read
  `sales_commissions` when they run.
- `expenses`: `expenses`, `expense_attachments`, the `expense-attachments` bucket (no storage policies;
  files go through the service role), the expense RPCs (`record_`, `submit_`, `approve_`, `reject_`,
  `post_`, `reimburse_`, `cancel_expense_atomic()`) and their helpers, and the foreign key
  `production_expenses.finance_expense_id` (a link with production, see above). `expense_categories` and `document_expenses` stay in core.
- `hr`: `employee_leaves` and the leave helpers `hr_leave_days_in_month()` / `hr_unpaid_leave_deduction()`.
  `employees` and `employee_departments` stay in core: profiles, sales, production orders and modules
  that do not depend on hr (consignment, expenses) point to them.
- `payroll`: `payrolls`, `employee_advances`, `calculate_monthly_payroll_drafts()`, `pay_payroll_run_atomic()`,
  `pay_employee_advance_atomic()`. `salary_payments` stays in core: `payrolls.salary_payment_id` and
  `sales_commissions.payroll_id` both point to it, and payroll and commissions do not depend on each other.
- `production`: production orders, materials, stock reservations, contractors, contracts, outsourcing,
  expenses, production BOMs, and the production RPCs and event processors. `product_bom` (product kits,
  with `create_product_with_bom_atomic()`) and `purchase_requests` (shared with purchasing) stay in core.
  The foreign keys from core tables (`sales`, `transactions`, `purchase_requests`) to `production_orders`
  install with production; those with crm (`deals`, `quotations`) and expenses are links (see above).
- `polywood`: `polywood_inventory_items` (rows of the Polywood stock import). Cut sheets (`polywood_pieces`) and
  the mixed-dimensional sale RPCs stay in core: sales, purchases, stock transfers, inventory counts, initial
  balance and production use them.
- `purchases`: `purchase_items`, `supplier_delivery_ratings` and the purchase workflow RPCs (draft save/post,
  receipt, cancel/void, document numbers). `purchases` itself stays in core with `suppliers`: partner payables,
  reconciliation, payments, the GL views and supplier AP read it, some from SQL functions that need the table
  when they are created. Its own triggers (`purchases_default_posted_when_blank`, partner sync) stay in core.
- `sales`: the sales invoice workflow RPCs (draft save/post, invoice event, GL and COGS posting, FIFO cost of
  sold items, stock restore, cancel/void, document numbers). No tables: `sales` and `sale_items` stay in core
  (receivables, reconciliation, payments, partner merge, inventory costing and cut sheets use them), with the
  `sales` triggers and the stock functions they call.
- `inventory`: stock counts, stock transfers, write-offs and initial balances (tables and RPCs, including
  `get_warehouse_active_categories()` used by counts). The stock engine stays in core: `warehouses`,
  `warehouse_stocks`, `stock_movements`, inventory batches (FIFO), warehouse slips and `polywood_pieces`.
- `accounting`: the GL balance sheet, general ledger and P&L report RPCs and the supplier opening balance.
  The ledger stays in core (chart of accounts, accounts, transactions, journal entries and lines, accounting
  periods, partners, GL views, journal posting, trial balance, partner balances): every posting module uses it.
